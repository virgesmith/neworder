# Developer

*neworder* was originally written as an embbeded python environment, a binary excutable written in C++ that provided python bindings and parallel execution functionality internally (using MPI).

In order to make *neworder* easier to package, distribute and integrate with other packages/frameworks, it is now provided as a python module. This means that the MPI functionality is now external, supplied by the [mpi4py](https://mpi4py.readthedocs.io/en/stable/) package.

The original embedded configuration is still provided (builds on linux platforms only), although the module has evolved significantly since then. See the "embedded" branch if you're interested.

## Development environment

See [system requirements](index.md#system-requirements). You will also need a C++20 compiler and [uv](https://docs.astral.sh/uv/). Then, from the repo root:

```bash
uv sync --dev
uv run pre-commit install
```

This creates a virtual environment in `.venv`, builds the C++ extension module, and installs the development tools. The pre-commit hooks keep `uv.lock` up to date and run `ruff` and `ty` on each commit.

Optional functionality is enabled with extras:

```bash
uv sync --dev --extra geospatial
uv sync --dev --extra parallel-openmpi  # or parallel-mpich, or parallel-native to use a system MPI installation
```

!!! warning "Extras"
    `uv sync` removes any extras that aren't named on the command line, so include all the ones you need every time,
    e.g. `uv sync --dev --extra geospatial --extra parallel-openmpi`.

After changing the C++ code, rebuild the extension. `uv sync` may not detect the change, so force a rebuild:

```bash
uv sync --dev --reinstall-package neworder
```

To use a specific compiler, set it in the environment, e.g.

```bash
CC=clang CXX=clang++ uv sync --dev --reinstall-package neworder
```

And a simple test that all is ok:

```bash
uv run python -c "import neworder"
```

## Quality checks

All of these must pass before a PR can be merged (CI runs them on Python 3.13-3.14, including the free-threaded 3.14t build, on linux, macOS and Windows. Python 3.15 is also tested, but is experimental and allowed to fail):

```bash
uv run ruff check
uv run ruff format --check
uv run ty check neworder examples test
uv run pytest
```

## Test

Tests use the `pytest` framework and can be invoked serially with

```bash
uv run pytest
```

and in parallel by running in MPI (this requires one of the `parallel-*` extras):

```bash
mpiexec -n 2 uv run pytest
```

!!! warning "Parallel testing"
    If the tests are invoked in parallel, but without an installed `mpi4py` package, they will run independently, as if in serial mode, and the interprocess tests won't get run. If in doubt check the test log for warnings.

## Running the Examples

The test suite doesn't exercise the examples, so run any affected by your changes. Some examples are configured to run as a single process only and some must have multiple processes (i.e. MPI). If the latter, prefix the python call with `mpiexec -n <N>`:

```bash
uv run python examples/<name>/model.py
```

or

```bash
mpiexec -n <N> uv run python examples/<name>/model.py
```

See the Examples section for details on each example.

## Documentation

The documentation is built with [zensical](https://zensical.org/) from the markdown in `docs/`, configured in `zensical.toml`. Its dependencies are in the separate `docs` dependency group, which `uv sync --dev` doesn't install. To preview it locally:

```bash
uv run --group docs zensical serve
```

The [API](./api.md) page is generated by mkdocstrings from the type stubs in `neworder/*.pyi`, so any change to the public API needs a corresponding stub change (see below). Builds are cached, so use `uv run --group docs zensical build --clean` if a stub change doesn't show up.

[neworder.readthedocs.io](https://neworder.readthedocs.io) is rebuilt automatically on pushes to main ("latest") and on release tags ("stable").

## Test Coverage

Coverage of both the C++ and the python code is reported to [codecov.io](https://codecov.io/gh/virgesmith/neworder/) by the [coverage workflow](https://github.com/virgesmith/neworder/blob/main/.github/workflows/coverage.yml). To reproduce it locally (on linux, with gcc):

```bash
uv sync --dev
CXXFLAGS=--coverage uv run --no-sync --with setuptools python setup.py build_ext --inplace --force
uv run --no-sync --with pytest-cov pytest --cov=neworder --cov-report=xml:coverage-py.xml
uvx gcovr --root . --filter src/ --xml coverage-cpp.xml --print-summary build
```

The extension is rebuilt in place because gcov writes its output (`*.gcda` files) next to the object files, and `uv sync` builds in a temporary directory that is deleted afterwards. `--no-sync` stops `uv run` replacing the instrumented build. Run `uv sync --dev --reinstall-package neworder` afterwards to restore a normal build. The `gcc` and `gcov` versions must match, otherwise `gcovr` will fail to read the coverage data.

## Type stubs

The type stubs for the C++ extension module are maintained by hand in `neworder/`: `__init__.pyi` (the core API plus the pure-python re-exports) and `time.pyi`, `mpi.pyi`, `stats.pyi` and `df.pyi`. These are what type checkers, IDEs and the API documentation see, so they must be kept in sync with the bindings in `src/Module.cpp` and the docstrings in `src/Module_docstr.cpp`.

They are seeded from the output of `pybind11-stubgen`, which can be regenerated (after rebuilding the extension) with:

```bash
uv run pybind11-stubgen _neworder_core --ignore-all-errors
```

`--ignore-all-errors` is required because `pybind11-stubgen` can't parse a default argument that is a function. The output goes to `stubs/_neworder_core/` (which isn't under version control). Don't copy it over the files in `neworder/`. Instead, port across only the genuine API changes, since the hand-maintained stubs contain corrections that would otherwise be lost:

- more precise types than the generated ones (e.g. pandas types in `df.pyi`, typed `*args` for `SplitMix64`)
- re-exports of the pure-python API in `__init__.pyi`
- an implementation signature following module-level `@overload`s (e.g. `time.isnever`). Without it the function is omitted from the API documentation.
- docstrings for module constants (e.g. `time.NEVER`, `mpi.RANK`), so they appear in the API documentation

## Release Checklist

!!! Note "Development Process"
    Development follows the typical cycle of issues :material-arrow-right: PR with CI :material-arrow-right: main
    ensuring code quality/correctness. Remember that type stubs may need to be updated if any changes are made to
    the extension module.

When a release is ready:

1. Ensure version in pyproject.toml has been updated (to say `X.Y.Z`)
1. Create a release in github, using a new tag `vX.Y.Z` and release notes based on commits since previous release, e.g.: `git log vX.Y.W..HEAD --oneline`. CI will then:
    - publish the release to PYPI
    - generate examples artifacts - these should be copied to the release

Note:

- [neworder.readthedocs.io](https://neworder.readthedocs.io) should default "stable" to the latest tag. ("latest" will point to main)
- [zenodo](https://zenodo.org/) should automatically see the new tag too
